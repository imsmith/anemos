    2. How policies run

    Copy Markdown View Source

    Knowing a language's syntax tells you what you can write. Knowing its execution model tells you what the program will do. In Anemos, the important questions are which listeners receive an event, which state they share, and when an expression actually invokes host code.

    From text to a running policy

    The host loads source text. The load boundary checks its size and authority, the parser recognizes declarations, and the compiler builds executable handlers. The runtime installs those handlers, datasets, and schedules. Loading a rule does not execute its when body.

    An incoming event supplies an exact name, an optional context path, and a payload. The dispatcher finds subscribers, filters them by context, evaluates the eligible handlers, and executes the operations they produce. Conditions also receive events they subscribe to and may generate transition events.

    An event can reach several rules. Rules are listeners rather than an exclusive chain of alternatives. If two rules subscribe to MOTION, both eligible rules can run. Use if/elseif/else within a handler when you want mutually exclusive choices. Do not make correctness depend on one independent listener having run before another.

    The four kinds of name

    Most policy mistakes become easier to see when names are classified:

    NameExampleWho supplies it?
    Declarationgarage-motionThe policy author
    EventMOTION, SENSOR::motionThe event producer and policy agree
    Module and verbDEVICE::setThe host registers the implementation
    Binding?visitor, @message, $countEvent data or policy evaluation

    when SENSOR::motion subscribes to that event name. It does not call the SENSOR module. [SENSOR::motion] is a command and does call a module. The brackets distinguish an action from a subscription.

    A report and an interaction

    Two trigger keywords take things that arrive from outside, and they take different kinds of thing.

    when <EVENT> takes a report. A report is a claim about the world at the moment it arrives: motion was detected, the network is up. It has a truth, true unless its payload says state: false, and that truth stands until the next report of the same event. Reports are what compound triggers combine, what for <duration> dwells on, and what conditions watch.

    on <interaction> takes an interaction. An interaction is an occurrence, not a claim: a key was pressed, a user logged in, the policy booted. It has no truth, is never remembered, and fires its body once each time it happens. It can carry an unless guard, because that reads the world at the moment of firing. It cannot carry for, until or a compound form, because each of those asks the runtime to remember it.

    rule console {
  context "console" {
    on boot { log "console policy active" }
    on keypress "ESC" { log "cancelled" }
    on USER_LOGIN { log ?user }
    on shutdown { log "console policy retiring" }
  }
}

    boot and shutdown are raised by the runtime itself, inside the rule's own context: boot when the policy becomes active, on load, on a changed redeploy and on replay after a restart; shutdown when it stops being so, on unload, on a changed redeploy and when the runtime stops. A redeploy that changes nothing raises neither. The host raises the rest through Anemos.Runtime.interact/4; see embedding.

    Interactions are indexed under names beginning ON_, which is why when ON_BOOT is refused by the parser and dispatch/4 refuses an ON_ name: a report path may not carry an occurrence, nor the other way round.

    A context belongs to a listener

    Declare one context boundary per rule. Either of these forms expresses it:

    rule listen {
  context "building.garage" {
    when MOTION { log "heard" }
  }
}
    rule listen {
  context building.garage
  when MOTION { log "heard" }
}

    The latter form is convenient in longer definitions. Use a single path rather than several apparently independent context blocks: the compiler extracts one context for the declaration, not a separate access domain for every block. Nested contexts do not provide lexical path composition.

    For a boundary building.garage:

    Arriving contextAdmitted?
    building.garageYes
    building.garage.sensorYes
    buildingNo
    building.gardenNo
    building.garagebandNo
    AbsentNo

    A rule with no context boundary accepts any arriving context, including an absent one. The host is responsible for authenticating the path it places on events. The language's comparison does not establish who sent an event.

    State has a lifetime and an owner

    There are three ways to read values:

    ReadMeaningLifetime
    ?nameExternal/name resolutionCurrent event plus visible queries/datasets
    @nameA let or loop bindingCurrent handler evaluation
    $nameA set bindingRetained for this named rule across events

    Several when blocks in the same named rule can communicate through set. Different named rules have separate binding state. That state is not automatically divided by sensor, user, or arriving context. If two devices reach the same rule, they reach the same $count. To maintain per-device state, arrange separate rule identities or keep keyed state in a host module.

    This counter initializes lazily and then increments:

    rule count-motion {
  when MOTION {
    if not exists $count {
      set count = 0
    }
    set count = $count + 1
    log $count
  }
  when RESET {
    set count = 0
  }
}

    In one persistent runtime, MOTION, MOTION, RESET, MOTION logs 1, 2, and 1. RESET logs nothing. Repeating Anemos.run/2 four times cannot reproduce this sequence because each call creates fresh state.

    Persistent here means retained in a running runtime. State survives supported worker restarts, but is not an on-disk database and does not survive loss of the whole runtime or VM. Chapter 10 explains replacement and recovery.

    Bodies evaluate, then operations execute

    This distinction matters whenever host commands have side effects.

    A standalone command statement produces an operation for the dispatcher to execute after evaluating the handler. A command in an expression must supply a value immediately, so it invokes the host while the expression is evaluated.

    rule demonstrate-order {
  when GO {
    [AUDIT::record "statement"]
    let answer = [LOOKUP::read "value"]
    log @answer
  }
}

    Here LOOKUP::read runs while the handler is being evaluated. Only afterward does the dispatcher execute the queued AUDIT::record operation and log the answer. The source order alone is therefore not the order of all external side effects. These modules are illustrative host implementations, not bundled services.

    When sequencing host calls is essential, express the sequence through value bindings whose calls are evaluated in order, or provide a host verb that owns the whole operation. Do not treat a sequence of independent statements as a transaction.

    A failed value-position call aborts the rest of that handler's evaluation and reports an error. Previously evaluated calls and earlier queued operations are not rolled back. Errors returned by queued operations do not, in general, cancel later queued operations. This is especially relevant to demand.

    Put executable statements inside triggers

    Rules are compiled from their when and at blocks. A top-level set or log in a rule is not a rule initializer, even where the parser accepts it. Place initialization inside a handler, guarded by exists as in the counter. Inline data and query declarations are an exception: they are definitions installed at load time, not executable statements.

    Exercise: who owns the count?

    Give count-motion a context of garage, then send motion from garage.north followed by garage.south. What does it log?

    Answer: 1, then 2. Both paths are admitted to the same named rule. Context filtering changes reachability; it does not allocate independent copies of persistent bindings.
